# Clinical Value Analytics

An end-to-end analytics engineering pipeline for transforming clinical alert data into reliable hospital-level metrics.

The project demonstrates a production-style data workflow using **Databricks, dbt, Apache Airflow, Docker, and PostgreSQL**, with a focus on data transformation, data quality, and pipeline orchestration.

## Project Overview

The pipeline processes clinical alert data generated by healthcare AI products and produces aggregated metrics at the hospital level.

The main goal is to demonstrate how raw clinical event data can be transformed into **clean, validated, and analytics-ready datasets**.

The pipeline includes:

1. Raw data stored in Databricks Bronze tables.
2. dbt staging models for cleaning and validation.
3. dbt mart models for business-level metrics.
4. Airflow orchestration of the dbt pipeline.
5. Docker Compose for a reproducible local Airflow environment.
6. PostgreSQL as Airflow's metadata database.

## Data Model

### Bronze

The pipeline starts with three source tables:

* `bronze_alerts`
* `bronze_patients`
* `bronze_hospitals`

These represent the raw input layer.

### Staging

`stg_alerts` cleans and validates the raw alert data.

The model performs:

* Deduplication by `alert_id`
* Patient ID validation
* Priority validation
* Product validation
* Creation of an overall `is_valid` flag

Supported alert priorities:

```text
LOW
MEDIUM
HIGH
```

Supported products:

```text
Stroke
PE
ICH
```

Each alert receives individual quality indicators:

```text
is_valid_patient_id
is_valid_priority
is_valid_product
is_valid
```

This allows downstream models to distinguish between valid and invalid records rather than silently removing bad data.

## Hospital Alert Metrics

The final mart, `hospital_alert_metrics`, aggregates alert-level data by hospital.

It produces metrics including:

* Total alerts
* Valid alerts
* Invalid alerts
* Valid alert percentage
* Alerts with invalid patient IDs
* Alerts with invalid priorities
* Alerts with invalid products

Example output:

## Data Quality

Data quality is treated as part of the transformation pipeline rather than as a separate manual process.

The dbt project includes tests for:

* `not_null`
* `unique`
* `accepted_values`

The staging model also explicitly tracks invalid records using boolean quality flags.

This makes it possible to answer questions such as:

> How many alerts are invalid, and why?

rather than simply dropping invalid records.

## Airflow

The pipeline is orchestrated using Apache Airflow.

The DAG:

```text
clinical_value_pipeline
        │
        ▼
     run_dbt
        │
        ▼
   dbt run
        │
        ├── stg_alerts
        │
        └── hospital_alert_metrics
```

The Airflow task retrieves the Databricks connection from Airflow's connection manager and dynamically creates the dbt `profiles.yml`.

This means that Databricks credentials are **not hard-coded inside the dbt project**.

The DAG executes:

```bash
dbt run
```

against the dbt project mounted inside the Airflow container.

## Docker

Airflow is deployed locally using Docker Compose.

The environment contains:

* Airflow API server
* Airflow scheduler
* Airflow DAG processor
* PostgreSQL
* Shared dbt project
* Airflow DAGs and logs

This provides a reproducible local development environment without requiring a local Airflow installation.

## Running the Project

### 1. Start the infrastructure

```bash
docker compose up -d
```

### 2. Verify the containers

```bash
docker compose ps
```

### 3. Verify Airflow

```bash
docker compose exec airflow-scheduler airflow dags list
```

The expected DAG is:

```text
clinical_value_pipeline
```

### 4. Trigger the pipeline

```bash
docker compose exec airflow-scheduler airflow dags trigger clinical_value_pipeline
```

### 5. Check the task state

```bash
docker compose exec airflow-scheduler airflow tasks states-for-dag-run \
  clinical_value_pipeline \
  "<run_id>"
```

A successful run should report:

```text
run_dbt    success
```

## Key Engineering Decisions

### Keep data quality information

Invalid records are not immediately discarded.

Instead, the pipeline creates explicit validation flags so downstream users can measure data quality and understand why records are considered invalid.

### Separate staging and marts

The project follows a layered dbt architecture:

```text
Source → Staging → Mart
```

Staging focuses on cleaning and standardization, while marts focus on business-facing analytics.

### Keep credentials outside dbt

Databricks credentials are managed through Airflow connections and injected into a temporary dbt profile at runtime.

This keeps credentials out of source control.

### Orchestrate transformations with Airflow

dbt handles SQL transformation and testing, while Airflow is responsible for scheduling and orchestration.

This separation keeps transformation logic independent from workflow orchestration.
